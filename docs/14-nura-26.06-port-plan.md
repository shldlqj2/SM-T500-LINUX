# 14. Nura 26.06 기반 SM-T500 포팅 계획

## 채택한 기준과 현재 상태

2026-10-30 사용자가 **Nura 26.06을 새 기본 OS로 사용하고 기존 Tab A7 postmarketOS 포트에서는 필요한 기기 정보·지원 코드만 가져오는 방향**을 선택했다. [D014](decisions.md)가 이전 Debian 12·제조사 커널 우선·자체 initramfs 계획을 대체한다. systemd host PID 1, Docker, 터치 Xfce, microSD ext4, SM-T500 전용 범위와 복구 관문은 유지한다.

이 문서의 '기본 이미지'는 **공식 v26.06의 aarch64 패키지와 기본 구성으로 생성하는 rootfs**다. 다른 기기의 boot/DT가 든 이미지를 가져오는 의미가 아니다. pmbootstrap으로 공통 배포판 부분을 생성하고 SM-T500 기기 패키지·커널·DT·firmware 변경을 별도로 연결한다. [N1](research/nura-n1-rootfs-2026-10-30.md)에서 rootfs 준비물을 생성했고 [N2](research/nura-n2-dt-2026-10-30.md)에서 공식 LTS·시험 DT·표준 initramfs 연결과 install을 검증했다. boot 계약·대응 SD 이미지·실기기 검증이 남아 있어 N2 전체는 부분 완료다.

## 기준 입력과 고정 범위

| 입력 | 현재 기준 | 상태 |
| --- | --- | --- |
| 배포판 | Nura `v26.06`, Alpine `3.24-stable`, `aarch64` | 사용자 선택·공식 릴리스 자료 확인 |
| pmaports | `https://gitlab.nura.eco/postmarketOS/pmaports.git`, `v26.06`, `2a8621d64d91647f7362eac59e7cdc091ff2bba8` | N1에서 checkout·메타데이터 APK 빌드 완료. kernel 빌드 미실행 |
| 공통 base recipe | 위 commit의 `main/postmarketos-base/APKBUILD`, `62-r0` | N1 rootfs의 실제 설치 패키지도 62-r0 |
| pmbootstrap 요구 | 위 pmaports.cfg의 최소 버전 `3.11.0` | 실제 사용 도구 3.12.1로 충족 |
| pmbootstrap 실행 기준 | `46ee403e4680002ce42dc2645adf9b08557270e9`, 3.12.1 | 별도 WSL 작업 디렉터리에서 실행·검증 |
| 오프라인 평가 커널 | 위 pmaports commit의 `linux-postmarketos-lts` recipe `6.18.35-r0` | D015에 따라 공식 APK·최종 config·모듈 검사 완료. kernel 로컬 재빌드·실기기 부팅 미검증 |
| 순정 하드웨어·복구 자료 | 제공 `T500XXS8CXG1` 패키지 | [정적 조사](firmware/T500XXS8CXG1.md) 완료, One UI 실기기 전환 미실행 |
| 기존 Tab A7 자료 | [기존 포트 검토](research/postmarketos-gta4l.md)의 고정 downstream/mainline commit | 선택적 재사용을 위한 비교 자료 |

branch는 움직일 수 있으므로 실제 빌드에서는 위 기준 SHA와 로컬 변경을 기록한다. APK 저장소도 릴리스 채널을 v26.06/Alpine 3.24로 고정하고 apk 서명 검증·정확한 설치 패키지 버전·APK 해시를 보존한다. branch SHA만으로 바이너리 저장소까지 불변이 된다고 판단하지 않는다. edge 패키지를 조용히 섞거나 버전 이름만 26.06으로 바꾸지 않는다.

Nura 릴리스 번호는 단일 kernel 버전을 지정하지 않는다. 공식 generic LTS recipe를 우선 평가하되 필요한 SM6115·패널·터치 지원이 부족하면 같은 26.06 사용자 공간을 유지한 채 필요한 kernel 패치 또는 다른 유지되는 kernel 기준을 비교한다. 기존 포트의 6.10·4.19.300을 기본값으로 상속하지 않는다. 커널을 변경하는 실험은 별도 입력 세트로 식별한다.

systemd의 실제 Nura 패키지 요구사항과 upstream 요구사항을 모두 확인한다. 관측한 pmaports.cfg는 systemd kernel 최소 5.4·권장 5.7을 선언하지만, upstream systemd v261 README는 최소 5.10·권장 5.14를 설명한다. 이 차이를 무시하고 4.19 기반을 초기 부팅 커널로 채택하지 않는다. Nura 패치·최종 config와 실제 런타임 요구를 확인하며 단순 버전 비교만으로 호환성을 확정하지 않는다.

## 기존 포트에서 가져올 범위

프로젝트의 기기 패키지 식별자는 `device-samsung-gta4lwifi`다. SM-T500 전용이며 기존 통합 gta4l 패키지의 LTE 이름·모뎀 설정을 승계하지 않는다. [현재 패키지](../ports/device-samsung-gta4lwifi/README.md)는 N1 metadata-only 0.1-r0에서 N2 0.2-r0으로 바뀌어 공식 LTS·시험 DT와 PHY 모듈을 연결한다. firmware·boot header/offset·flash 지원은 미구현이다.

| 기존 자료 | 가져올 후보 | 반영 전 확인할 것 |
| --- | --- | --- |
| deviceinfo | 모델·아키텍처·화면 방향·기기 특성의 근거 | SM-T500 실물·순정 자료·v26.06 deviceinfo 규격과 대조해 필드별 작성 |
| board DTS/패치 | 실제 연결 bus·GPIO·regulator·panel·touch·reserved-memory 정보 | upstream SoC DTSI와 선택한 kernel의 binding에 맞춰 필요한 보드 변경만 이식 |
| kernel 설정 | 빠진 드라이버·기능을 찾을 단서 | Nura의 kconfig 검사와 systemd/Docker 요구에 맞는 작은 fragment로 표현 |
| firmware 패키지 | 필요한 파일 이름·출처·요청 경로·로딩 순서 | 실제 장치와 driver의 요청, 파일 해시·라이선스·보정 자료 의존성 확인 |
| modules-initfs | 초기 저장소·USB·firmware 의존 후보 | 선택한 kernel의 built-in/module 여부와 모듈 이름·의존성 대조 |
| udev·터치 보정 | 화면 방향·좌표 변환의 단서 | 실제 패널·Xfce/libinput 경로에서 재검증, 중복 변환 방지 |
| 기존 빌드/설치 기록 | 실패 증상·초기화 순서의 단서 | 실제 소스·이미지·모델·재현 조건과 연결 |

각 도입 항목에는 원본 URL·commit·파일·라이선스/저작권·원본 해시·필요 이유·변경 내용·검증 상태를 기록한다. 기존 기능표를 실기기 결과로 옮기지 않는다. 소스가 있는 부분은 정상 소스 분석으로 읽고, REA는 필요한 비공개 모듈·HAL·firmware 구조의 미확인 부분에 사용한다.

기존 rootfs/prebuilt 이미지, 배포판 저장소·기본 계정·서비스 정책, 오래된 kernel/config 전체, 근거 없는 offset, LTE 전용 설정, userdata 설치 지침, U-Boot/부트로더 변경은 기본 입력에 포함하지 않는다. 특히 기존 deviceinfo의 ramdisk offset `0x20000000`과 순정 header의 `0x02000000`은 해석·최종 이미지·기기 대조 전 채택하지 않는다.

## 생성·부팅 구조

~~~text
공식 Nura v26.06 패키지 + SM-T500 전용 변경
  → pmbootstrap / Nura 표준 패키징·initramfs
  → kernel + DT + 대응 modules/firmware + boot image
  → 기존 Samsung bootloader
  → microSD ext4의 Nura rootfs
  → systemd (host PID 1)
      ├─ udev / SSH / 네트워크
      ├─ Docker Engine (linux/arm64)
      └─ Xfce / 터치 / 화면 키보드 / 회전
~~~

Nura 표준 initramfs·서비스를 먼저 사용하고 USB 진단·SD 탐색 등 부족한 기능만 작은 기기별 변경으로 추가한다. 별도 BusyBox /init 전체를 새로 작성하는 것은 기본 구현에서 제외하고 학습 실습으로 남긴다. pmbootstrap의 실제 initramfs/boot-deploy·패키지 업데이트 경로를 확인하기 전 예전 custom init 계약을 구현된 동작으로 취급하지 않는다.

microSD 부팅은 현재 구현·실기기 검증되지 않았다. SD 없음·잘못된 UUID·필수 모듈 누락은 진단 상태로 처리하고 내부 rootfs로 자동 대체·포맷하지 않는다. 내부 userdata rootfs 설치와 부트로더·PIT 변경은 범위 밖이다. 기존 bootloader가 SD를 직접 읽거나 fastboot 임시 부팅을 지원한다고 가정하지 않는다.

## 단계와 통과 조건

| 단계 | 작업 | 완료 증거 |
| --- | --- | --- |
| N0 기준·재사용 목록 | 공식 입력 고정, 기기/firmware/DT 도입 후보 평가 | 버전·SHA·출처·해시 및 항목별 채택/수정/제외 목록 |
| N1 도구·최소 rootfs | 검증한 Linux 환경에 pmbootstrap 준비, v26.06 aarch64 콘솔 구성 생성 | 도구 버전·저장소·apk 서명·패키지 명세·os-release·로그·이미지 해시 |
| N2 기기 패키지·커널 | SM-T500 deviceinfo·DT·config·modules/firmware·SD/USB 의존성 구현 | 최종 .config·DTS 검사·산출물 대응표·정적 boot 분석 |
| N3 복구 가능한 부팅 | docs/03 관문 후 실제 kernel·initramfs·SD rootfs 시험 | 관측 로그·systemd PID 1·SD 실패 처리·정상 이미지 복구 |
| N4 서비스·GUI·무선 | Docker·Xfce·터치·Wi-Fi·Bluetooth 순차 검증 | docs/11의 네트워크·볼륨·자원 제한·터치 조작·회귀 시험 |

N0~N2의 오프라인 조사·이미지 생성은 One UI 재설치와 독립적으로 진행할 수 있다. 실기기 기록은 [docs/03](03-backup-and-recovery.md)의 관문을 통과한 뒤 한다. 최초 kernel·DT·initramfs·rootfs 연결은 의존 변경을 포함하는 N3 초기 실험 세트로 명시하고, 그 이후에는 한 층씩 변경한다.

N1에서는 kernel 없는 최소 device package로 패키지 트리를 준비했다. 당시 `pmbootstrap install --no-image`는 mkinitfs의 kernel/flavor 검사에서 종료 1이었다. ARM64 chroot·systemd version·패키지 신뢰 연결을 검사하고 ext4 rootfs-only 준비 이미지로 별도 저장했다. N2의 별도 작업 공간에서는 kernel/flavor를 연결해 install·mkinitfs가 종료 0으로 통과했다. N2 rootfs는 383개 패키지 트리이며 ext4 파일로 내보내지 않았다. N1 이미지는 N2 대응 모듈이 없으므로 결합하지 않는다. 표준 initramfs의 SD UUID/실패 정책·boot 생성 경로는 후속 검증 대상이다.

GUI 목표는 기존 Xfce를 유지한다. v26.06에서 실제 제공되는 UI·greeter·화면 키보드 패키지와 systemd 조합을 확인한 뒤 설치 명세를 확정한다. 초기에는 콘솔·SSH부터 검증하고, 터치 변형은 실기기 DT/bind/firmware와 대조한다.

## 도구와 문서의 적용

이미지·패키지 생성은 pmbootstrap/Nura 도구가 담당한다. 기존 portctl 수집기는 조사·보고에 계속 사용한다. 미구현 sources/build/artifacts CLI는 기존 설계이며 pmbootstrap과 중복되는 자체 빌드 엔진의 우선 구현 계획은 대체됐다. 필요한 재현/해시 기록 연동을 설계한 뒤 [데이터 계약](design/03-data-contracts.md)을 변경한다. 현재 코드·계약을 구현 없이 변경된 것으로 표시하지 않는다.

기존 [부팅 계약](05-boot-and-image-design.md)·[검증 기준](11-validation-and-milestones.md)의 복구·해시·PID 1·기능 합격 원칙은 유지한다. Debian debootstrap·apt·systemd 252와 제조사 4.19 필수 재현을 전제한 설명은 이 계획으로 대체한다. [D013](decisions.md)의 One UI는 실제 하드웨어 관측·firmware 출처·복구 기준으로 유지하며 Nura rootfs를 대체하지 않는다.

## 이번 조사 증거와 한계

Windows PowerShell/Python·저장소 루트에서 git ls-remote 및 공개 raw 파일을 읽었다(명령 종료 0). pmaports v26.06 SHA와 공개 pmbootstrap HEAD를 기록하고 base recipe·pmaports.cfg·generic kernel recipe 3개를 확인했다. 원본·URL·크기·SHA-256·실패한 추정 경로는 `private/research/nura-26.06-baseline/upstream-observations.json`에 있다. kernel 패키지의 올바른 경로는 `device/main/`이며 처음 조회한 `main/` 경로의 404를 패키지 부재로 해석하지 않았다.

위 조사는 계획 수립 시점의 기록이다. 이후 N1에서 pmbootstrap 3.12.1·mount/chroot·ARM64 binfmt/QEMU user·공식 패키지 설치와 rootfs 파일 생성을 검증했다. N2에서는 DT·기기 APK 빌드·공식 kernel 설치·표준 initramfs 생성·해시/신뢰 경로 검사를 완료했다. 전체 DT binding 검사에는 upstream 비교군과 동일한 GPU 진단이 남아 있다. kernel 전체 소스 빌드·boot.img 생성·기기 시험은 미실행이다. 공식 문서가 WSL을 공식 지원 환경으로 보장하는 것은 아니며 이번 작업의 구체적 동작 범위만 검증한 것이다.
