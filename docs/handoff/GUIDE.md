# 인수인계 작성·수신 지침

## 목적과 문서 역할

대화 기록 없이도 다른 에이전트가 현재 상태를 확인하고 다음 작업을 이어가게 한다. 사용자의 의도, 실제 기기 상태, 코드·이미지 대응 관계, 실패 증거를 보존한다.

| 문서 | 역할 |
| --- | --- |
| [AGENTS.md](../../AGENTS.md) | 모든 에이전트의 필수 작업 규칙 |
| [README.md](../../README.md) | 프로젝트 목표와 문서 탐색 |
| [HANDOFF.md](../../HANDOFF.md) | 최신 상태와 다음 행동의 단일 진입점 |
| [TEMPLATE.md](TEMPLATE.md) | 최신 인수인계·이력 작성 양식 |
| [결정 기록](../decisions.md) | 장기 선택·이유·변경 조건 |
| history/의 시점별 기록 | 실제 인수인계 시 보존하는 과거 상태 |

현재 인수인계 문서는 작업 상태를 설명한다. 새로운 권한을 부여하거나 현재 세션의 Plan 모드를 해제하지 않는다. 명령 예시는 실행 조건을 확인하기 전 자동 실행하지 않는다.

## 작성 시점

- 세션 종료 또는 다른 에이전트로 이전하기 전.
- 부팅·복구·핵심 기능 시험을 완료한 뒤.
- 커널·DT·firmware·rootfs 기준이 바뀐 뒤.
- 기기에 이미지를 기록한 뒤.
- 기존 가설이 반증되거나 설계가 바뀐 뒤.
- 작업 중단·결과 미확인·접근 제한 때문에 다음 작업자 판단이 필요한 경우.

진행 중 기록 작업을 문서 갱신 때문에 중단하지 않는다. 도구 로그와 이미지 ID를 먼저 보존하고 결과 관측 후 갱신한다. 비정상 중단은 성공/실패를 추측하지 말고 결과 미확인으로 남긴다.

## 반드시 구분할 것

| 구분 | 예시 |
| --- | --- |
| 사용자 확인 | '부트로더를 해제했다'는 사용자 설명 |
| 실측 사실 | 날짜·기기·명령·로그가 있는 boot 상태 |
| 공개 자료 | 특정 source SHA의 BoardConfig 설정 |
| 설계 결정 | Debian 12·Xfce·microSD 선택 |
| 가설 | regulator 의존성 때문에 probe가 지연된다는 추론 |
| 미확인 | 현재 vendor 버전·복원 성공 여부를 아직 보지 못함 |

계획을 과거형으로 바꿔 완료처럼 쓰지 않는다. '빌드됨', '이미지 기록됨', '부팅됨', '기능 검증됨'은 서로 다른 상태다. 외부 자료의 동작 보고를 우리 기기의 결과로 복사하지 않는다.

## 작성 절차

1. 현재 Git branch·HEAD·status와 작업 디렉터리를 읽기 전용으로 확인한다.
2. 미커밋·미추적 변경과 소유 주체를 나눈다. 첫 commit이 없으면 HEAD 없음을 명시한다.
3. 현재 작업·기기·실행 프로세스 상태를 확인한다. 오래된 관측은 마지막 확인 시각을 쓴다.
4. 완료 작업마다 증거 경로와 검증 범위를 연결한다.
5. 실패·미완료·시도한 방법·반복할 필요 없는 접근을 적는다.
6. 마지막 기기 변경과 정상 복귀 이미지 세트를 적는다.
7. 다음 작업을 최대 3개로 정하고 각 완료 조건을 쓴다.
8. 최신 HANDOFF.md를 갱신한다.
9. 실제 소유권 이전 시 같은 내용을 history/YYYY-MM-DDTHH-mm-ss+0900-주제.md로 보존한다.
10. 수신자의 파일·자료 접근 및 전달 상태를 확인한다.

기존 이력 파일은 덮어쓰지 않는다. 정정은 새 기록에 남기고 원래 기록을 연결한다. 단순 작업 종료마다 history를 불필요하게 생성할 필요는 없다.

## 기기 상태의 최소 정보

- 민감 일련번호 대신 사용할 기기 별칭과 정확한 모델.
- 현재 실행 OS·boot 모드·연결 상태·마지막 관측 시각.
- 마지막으로 기록한 대상 파티션·이미지 ID·해시·결과.
- boot/DT/module/rootfs/firmware 세트의 대응 관계.
- 정상 이미지 위치와 복원 시험 여부.
- 현재 기록·재부팅 작업 소유자, 작업 중 여부.
- 기기가 원격 호스트나 다른 사람에게 연결되어 있다면 접근 조건.

기기 상태를 확인하지 않았으면 '사용자 설명'과 '미관측'으로 표시한다. 문서를 읽는 동안 기기 상태가 바뀌었을 수 있으므로 수신자는 기록 전에 다시 확인한다.

## 명령·실행 프로세스 기록

재현에 필요한 명령은 실행 환경, cwd, 도구 버전, 시작 시각, 종료 코드, 로그 위치를 함께 남긴다. token·password·serial·계정 정보는 제거한다.

진행 중 빌드·다운로드가 있으면 host, 작업 경로, PID/세션·터미널 식별자, 로그, 재접속 방법을 적는다. runtime handle은 재시작 후 무효화될 수 있다. '응답이 없으니 다시 시작'하지 말고 실제 프로세스를 먼저 확인한다.

프롬프트 전달의 입력 수락은 실제 작업 시작 증거와 다르다. 전달됨·입력 수락·작업 시작·검증 완료를 구분한다.

## 다른 checkout·다른 PC로 옮길 때

새 worktree에는 미커밋 파일·미추적 파일·Git 밖의 이미지가 자동으로 옮겨지지 않는다. 다음을 별도로 전달한다.

| 자료 | 전달 기록 |
| --- | --- |
| 추적된 코드 | 기준 commit과 branch, 필요한 patch |
| 미커밋 변경 | 파일 목록·diff 또는 명시적으로 복사한 파일, 검증 결과 |
| 미추적 문서·설정 | 정확한 파일 목록과 전달 후 내용 확인 |
| 대용량 이미지 | 비공개 위치, 접근 방식, 크기·SHA-256 |
| 로그·개인 백업 | 접근권한·민감정보 여부·공유용 요약 |
| 기기 연결 | 물리 위치·현재 연결 PC·접근 가능 여부 |

첫 commit이 없는 저장소에서는 'branch를 가져오면 된다'고 쓰지 않는다. 사용자가 요청한 전달 방식으로 실제 파일을 확보하게 한다. 요청 없이 커밋·푸시·공개 업로드를 하지 않는다.

문서 내부 링크는 상대 경로를 사용한다. host 절대 경로가 필요한 비공개 자료에는 어느 PC/WSL의 경로인지 명시한다. 수신자가 접근하지 못하면 미전달로 표시한다.

## 수신 에이전트의 첫 절차

1. AGENTS → README → HANDOFF → 관련 기술 문서·결정 기록 순서로 읽는다.
2. 기기 기록 명령보다 먼저 현재 checkout과 변경 목록을 비교한다.
3. 실행 중인 작업과 마지막 결과 미확인 항목을 확인한다.
4. 이전 검증 증거를 읽고 영향 없는 완료 작업은 반복하지 않는다.
5. 필요한 이미지·로그·백업에 접근할 수 있는지 확인한다.
6. 다음 작업과 현재 사용자 요청·권한 범위가 일치하는지 확인한다.
7. 기기 변경은 한 작업자만 수행하도록 소유권을 확인하고 재개한다.

기록과 실물이 다르면 차이를 먼저 기록한다. 새 코드 변경을 덧붙여 불일치를 숨기지 않는다.

## Orca를 이용한 실제 이전

이 프로젝트의 핵심 인수인계는 Markdown이므로 다른 에이전트 도구에서도 사용할 수 있다. Orca를 실제로 사용할 때는 그 세션의 orca-cli 스킬과 버전에 맞는 가이드를 읽는다.

- 문서 작성 요청은 새 worktree·agent 실행 요청이 아니다.
- 실제 전체 인수인계 요청에서는 source checkout과 전달할 변경을 먼저 확정한다.
- 새 worktree ID 전체와 agent handle, 전달 receipt를 기록한다.
- TUI 준비를 확인한 뒤 전달하고 accepted 결과를 검사한다.
- accepted는 입력 수락이며 작업 시작과 구분한다. 무응답만으로 중복 전달하지 않는다.
- 소유권 이전 후 기존 에이전트는 같은 작업을 계속 수정하지 않는다.
- 사용자가 감독을 요청하지 않았다면 완료를 기다리는 orchestration 작업으로 바꾸지 않는다.

구체적인 Orca 명령은 버전·실행 환경에 따라 달라질 수 있어 이 문서에 영구 실행 명령으로 고정하지 않는다.

## 전달용 짧은 메시지 양식

~~~text
프로젝트: SM-T500 Native Linux
작업 위치/전달한 checkout:
먼저 AGENTS.md → README.md → HANDOFF.md를 읽으세요.
목표:
현재 단계와 검증 완료 범위:
전달한 미커밋·미추적 파일:
접근해야 할 비공개 자료와 전달 여부:
다음 작업 및 완료 조건:
기기 변경 담당자/진행 중 작업/결과 미확인 사항:
현재 요청 범위와 보류 조건:
~~~

## 품질 검사

- [ ] 사용자에게 이미 확인한 내용을 다시 물을 필요가 없다.
- [ ] 첫 행동과 완료 조건을 찾을 수 있다.
- [ ] 계획·실행·검증이 구분되어 있다.
- [ ] 실패와 결과 미확인이 숨겨져 있지 않다.
- [ ] 마지막 기기 변경·정상 복귀 세트를 알 수 있다.
- [ ] 로그·이미지·미커밋 파일의 접근·전달 여부가 정확하다.
- [ ] 기기 제어 소유자가 중복되지 않는다.
- [ ] 민감 자료와 비밀값을 포함하지 않는다.
- [ ] 문서 링크가 실제 파일을 가리킨다.
