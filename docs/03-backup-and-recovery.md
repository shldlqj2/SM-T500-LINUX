# 03. 백업과 복구

## 목적·필수 조건

커스텀 부팅 실패를 없애는 것이 아니라, 실패 후 정상 이미지 또는 순정 One UI로 돌아갈 수 있는 검증된 경로를 확보한다. Knox 보안 상태의 원복은 목표가 아니다.

[기기 조사](02-device-investigation.md)에서 모델·파티션 매핑·크기·부트로더 리비전을 확인한 뒤 진행한다. 정확한 대상이 나오기 전에는 플래싱 명령을 만들지 않는다. 이 문서는 복구 절차의 기준 문서이며 다른 문서는 여기로 연결한다.

## 복구의 두 수준

| 수준 | 목적 | 보존할 것 |
| --- | --- | --- |
| 실험 복구 | 마지막 정상 LineageOS/Debian으로 복귀 | 정상 boot, 대응 DT·모듈·rootfs, 기록 대상 목록 |
| 순정 복구 | Samsung One UI로 재설치 | SM-T500용 검증된 순정 패키지, 리비전·지역 정보, 도구·설치 기록 |

순정 복귀는 개인 데이터 복구, 기존 루팅 유지, Knox 복원과 다르다. 커스텀 OS 기록 후 부트로더를 다시 잠그는 작업은 이 계획에 포함하지 않는다.

## 백업 대상

1. 사용자가 보존할 파일과 앱 데이터. Android 암호화 때문에 raw userdata만으로 복구 가능하다고 가정하지 않는다.
2. 현재 ROM 원본 설치 패키지·부팅 이미지 및 현재 루팅 이미지. 둘을 구분한다.
3. 실제 존재하는 boot, recovery, dtbo, vbmeta 관련 파티션.
4. 실제 존재하는 efs, sec_efs, persist 등 기기 고유 데이터. 파티션 이름만으로 무조건 읽거나 복원하지 않고 역할·크기를 확인한다.
5. 파티션 맵, super 메타데이터와 필요한 vendor/odm 자료.
6. 커널 설정, DT, 펌웨어 목록·해시, 정상 부팅 로그.

실행 중 변경되는 파일시스템은 raw 이미지가 일관되지 않을 수 있다. 개인 데이터는 먼저 OS가 제공하는 방식으로 백업하고, raw 백업은 recovery에서 관련 파일시스템이 쓰이지 않는 상태를 우선한다. 암호화 키에 묶인 데이터의 복원 가능성을 별도로 기록한다.

## 백업 검증

- 기기 밖 PC에 최소 한 사본을 둔다. 중요한 개인·고유 자료는 별도 저장장치에도 보관한다.
- 백업 파일 크기와 실제 파티션 크기를 대조한다.
- 기기 측 읽은 내용과 PC 파일의 SHA-256을 가능한 범위에서 대조한다.
- 압축 파일은 컨테이너 해시와 압축 해제한 payload 해시를 구분한다.
- 이미지 분석·압축 해제 검사가 된 것과 실제 복원 시험이 된 것을 분리해 기록한다.
- EFS 등 고유 데이터는 검증만을 위해 덮어쓰지 않는다. 역할과 현재 정상 여부를 근거로 복원이 필요한 경우에만 다룬다.

Windows PowerShell의 텍스트 출력 경로를 raw 바이너리 백업에 쓰지 않는다. 전송 방법을 작은 비민감 바이너리로 시험하고 길이·해시를 확인한다.

## 순정 펌웨어 선정

모델 SM-T500, 지역/CSC, 현재 bootloader 리비전, 패키지 출처·무결성·구성 파일을 기록한다. LTE SM-T505 계열과 혼용하지 않는다. 롤백 방지 제한보다 낮은 부트로더를 기록하지 않는다.

가능하면 현재 리비전과 맞는 펌웨어를 사용한다. 상위 리비전만 가능한 경우 비가역적 리비전 상승 및 이후 실험 기준에 미치는 영향을 설명하고 기존 권한 범위와 대조한다. 호환 패키지가 없으면 순정 복귀는 미검증 상태로 남기며 Linux 기록 단계로 진행하지 않는다.

삼성 복구는 Download Mode 기반 도구를 사용한다. 현재 OS·도구 버전·기기에서 실제 통신 검증을 거쳐 도구를 고정한다. Heimdall·Odin 계열·LineageOS 안내 도구 간 지원 차이를 무시하고 임의로 교체하지 않는다. 이 단계에서 패키지 인수 형식과 기록 파티션 목록을 확정한다.

## 첫 복구 리허설

1. 개인·고유 데이터 백업의 위치와 무결성을 확인한다.
2. 전원 버튼 조합으로 Download Mode와 recovery 진입을 확인한다. 실제 기기에서 검증한 방법만 기록한다.
3. PC에서 정확한 기기 인식과 도구 통신을 확인한다.
4. 검증된 현재 정상 이미지의 복원 경로를 시험한다. 기록 대상과 읽기 검증을 남긴다.
5. 순정 One UI 재설치를 수행해 초기 부팅·기본 조작을 확인한다.
6. 실험 기준 ROM을 복원하고 부트로더·vendor·커널·AVB 상태를 다시 조사한다.
7. 새 상태를 기준으로 정상 이미지 세트와 문서를 갱신한다.

순정 설치 중 userdata 초기화가 필요할 수 있다. 이 가능성은 기존 요구에 포함되어 있지만 실제 데이터 백업 완료 여부를 별도로 검증한다. 도구의 repartition/PIT 변경 옵션은 기본적으로 사용하지 않는다.

## 실험 기록 전 체크

- [ ] 대상 모델과 기기 별칭이 맞다.
- [ ] 기록 담당자가 한 명이며 다른 기록·복구 작업이 없다.
- [ ] 대상 파티션의 이름·매핑·크기가 확인됐다.
- [ ] 이미지 해시·헤더·크기·DT 관계와 실제 기록 목록을 검증했다.
- [ ] 정상 recovery 및 Download Mode 복귀 경로를 확인했다.
- [ ] 되돌릴 이미지와 대응 rootfs·모듈이 PC에 있다.
- [ ] 전원·케이블이 안정적이고 충분한 배터리 상태다.
- [ ] 결과를 관측할 로그·콘솔 경로가 있다.
- [ ] 기록 작업이 현재 사용자가 요청한 실행 범위에 속한다.

## 기록 후 검증·실패 대응

가능한 경우 기록 영역을 읽어 이미지 길이만큼 비교한다. 전체 파티션 해시와 padding을 제외한 이미지 해시를 혼동하지 않는다. 도구가 읽기 검증을 지원하지 않으면 이를 명시하고 성공 메시지만으로 바이트 일치를 주장하지 않는다.

| 증상 | 대응 |
| --- | --- |
| 부트로더 이미지 거부 | 모델·헤더·AVB·크기·이미지 대응 관계 확인 후 정상 boot 복원 |
| 부팅 루프·검은 화면 | 확인한 키 조합으로 recovery/Download Mode 복귀, 로그 회수, 마지막 변경 제거 |
| initramfs에서 SD 없음 | SD 식별·컨트롤러·파일시스템 조사. 내부 저장소 포맷 금지 |
| systemd/GUI만 실패 | USB/SSH 진입 후 사용자 공간 로그 조사. 부트로더 변경 금지 |
| 기록 도중 연결 끊김 | 결과 미확인으로 표기. 현재 모드·파트 상태부터 확인하고 중복 기록 금지 |
| Download Mode도 관측 불가 | 충전·케이블·확인한 키 조합만 점검. 현재 분해 없는 범위의 한계로 보고 |

## 기록 양식·완료 조건

~~~text
복구 시험 ID / 시각 / 담당자:
기기 모델 / 펌웨어·리비전 전후:
사용 도구·버전 / PC 환경:
입력 패키지·이미지 ID / SHA-256:
기록한 실제 파티션 / 기록 결과 / 읽기 검증:
정상 부팅 및 기능 결과:
개인 데이터 영향 / 실패와 해결:
원본 로그 위치 / 재현 가능한 복구 절차 위치:
~~~

실험 복구와 One UI 재설치를 각각 관측·기록해야 초기 복구 관문을 통과한다. 이후 모든 실험에서 순정 재설치를 반복할 필요는 없다. 펌웨어나 복구 도구가 바뀌면 영향받는 부분만 재검증한다.
